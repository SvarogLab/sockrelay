# sockrelay

`sockrelay` — система из двух Rust-бинарников, которая проксирует именованный пайп Windows в unix
domain socket на стороне WSL/Linux через одно мультиплексированное соединение. Это универсальный,
протокол-агностичный релей байтов, а не proxy, специфичный под ssh-agent — но написан он был для
настоящего пайпа Windows OpenSSH `ssh-agent`, и пока проверялся только против него; именно этот
сценарий описан в остальной части README.

Она заменяет классический мост `socat` + `npiperelay.exe`, который спаунит новый Windows-процесс
на каждое подключение. При параллельном использовании SSH (например, Ansible, форкающий много
одновременных SSH-соединений) одновременный спаун Windows-процессов из WSL2 упирается в
реальный, задокументированный баг WSL2-интеропа
([microsoft/WSL #7371](https://github.com/microsoft/WSL/issues/7371),
[#6891](https://github.com/microsoft/WSL/issues/6891),
[#53250](https://github.com/microsoft/WSL/issues/53250)) и начинает падать с
"communication with agent failed". `sockrelay` спаунит Windows-процесс ровно **один раз** и
мультиплексирует через него все последующие соединения — так что условие срабатывания бага просто
никогда не наступает.

Сравнение нагрузочного тестирования против старого моста — в [BENCHMARKS.md](BENCHMARKS.md),
включая живую поимку отказа старого моста в том же прогоне.

## Архитектура

- **`sockrelay-client`** (WSL/Linux) демонизируется (форкается, отсоединяется от управляющего
  терминала — см. [Запуск](#запуск) ниже), затем слушает unix domain socket. При старте один раз
  спаунит **`sockrelay-server`** через анонимный pipe (stdin/stdout спаунутого процесса) и
  мультиплексирует каждое принятое unix-соединение через это единственное соединение с помощью
  [`yamux`](https://docs.rs/yamux). Если соединение с сервером умирает — демон завершается, а не
  тихо ретраит или респауннит; перезапуск ожидается от супервизора (например, systemd), как и для
  любого другого упавшего демона.
- **`sockrelay-server`** (Windows, кросс-компилируется и запускается через WSL binfmt interop — см.
  [Сборку](#сборка) ниже) принимает yamux-стримы от клиента и релеит каждый в свежий handle на
  настоящем именованном пайпе `ssh-agent`.

Всего два крейта — более ранний `sockrelay-common` (общие типы ошибок mux и хелпер релея байтов)
свернули обратно, когда выяснилось, что одна из двух его частей используется только одной
стороной: `MuxError` теперь дублируется дословно и в `client::mux`, и в `server::mux` (идентично,
9 строк — дешевле синхронизировать руками, чем поддерживать ради этого отдельный крейт), а хелпер
релея байтов переехал в `client::relay`, к своему единственному оставшемуся потребителю.

Отдельный инструмент нагрузочного тестирования, которым измерялось поведение проекта под
конкурентной нагрузкой против настоящего агента во время разработки, живёт в соседнем репозитории,
[`sockrelay-loadtest`](../sockrelay-loadtest) — он не часть этого workspace, поскольку не зависит
ни от одного из крейтов выше.

Ни `sockrelay-client`, ни `sockrelay-server` не разбирают байты, которые через них проходят — ни
фрейминга, ни границ сообщений, ничего, что предполагало бы конкретно wire-формат ssh-agent; оба
просто релеят сырые байты между unix-сокетом и именованным пайпом в обе стороны. Единственное
архитектурное решение, продиктованное реальным поведением ssh-agent (гонять обе стороны копирования
и закрывать обе, как только завершится любая, вместо `tokio::io::copy_bidirectional`, который ждёт
half-close с обеих сторон), на самом деле является исправлением свойства именованных пайпов Windows
**вообще** — у них нет настоящего half-close, — а не чего-то специфичного для ssh. Так что это
справедливо для любого протокола, релеящегося таким же образом.

## Конфигурация

`sockrelay-client` — это то, что реально запускает человек (обычно из shell-профиля), поэтому
у каждого его флага есть разумный дефолт, и запуск совсем без флагов работает в типичном случае.
`sockrelay-server` — другое дело: его спаунит `sockrelay-client`, а не человек напрямую, поэтому
каждый его флаг **обязателен**, без единого дефолта — он отказывается стартовать, а не молча
угадывает путь к пайпу или таймаут.

### `sockrelay-client`

```text
sockrelay-client
  --socket <PATH>                        дефолт: ~/.ssh/agent.sock
  --server-exe <PATH>                     дефолт: "sockrelay-server.exe", ищется через PATH
  --socket-mode <OCTAL>                   дефолт: 600
  --accept-error-backoff-ms <MS>          дефолт: 100
  --log-file <PATH>                       дефолт: не задан (файл не пишется) — см. Логирование ниже
  --foreground                            дефолт: выключен — см. Запуск ниже
  --pipe-path <PATH>                      дефолт: \\.\pipe\openssh-ssh-agent — пробрасывается спаунутому серверу
  --connect-timeout-secs <N>              дефолт: 5 — пробрасывается спаунутому серверу
  --jitter-max-ms <MS>                    дефолт: 50 — пробрасывается спаунутому серверу
```

```sh
sockrelay-client
```

этого достаточно, если `sockrelay-server.exe` есть в `PATH` (например, после того как
`install.sh` положит его в `/usr/local/bin`) — любой флаг выше можно явно переопределить:

```sh
sockrelay-client --socket ~/.ssh/agent.sock --server-exe /path/to/sockrelay-server.exe \
  --socket-mode 600 --pipe-path '\\.\pipe\openssh-ssh-agent'
```

Последние три флага (`--pipe-path`, `--connect-timeout-secs`, `--jitter-max-ms`) не влияют на сам
`sockrelay-client` — они читаются здесь только для того, чтобы быть переданными как аргументы
командной строки спаунутому `sockrelay-server.exe`. Это осознанное решение, а не избыточность:
переменные окружения, выставленные на `sockrelay-client`, **не** пересекают границу WSL
binfmt-интеропа в спаунутый Windows-процесс (проверено эмпирически) — поэтому argv единственный
канал, который туда надёжно доходит.

### `sockrelay-server`

Не предназначен для прямого запуска конечным пользователем — его спаунит `sockrelay-client`,
явно передавая каждый флаг (и его собственный `--help` прямо об этом говорит). Тем не менее
полезен для ручного тестирования против настоящего агента — каждый флаг ниже обязателен, без
дефолта:

```powershell
sockrelay-server.exe \
  --pipe-path '\\.\pipe\openssh-ssh-agent' \
  --connect-timeout-secs 5 \
  --jitter-max-ms 50
```

- `--connect-timeout-secs` ограничивает, сколько попытка подключения будет ждать насыщенный
  агент, прежде чем сдаться, при получении `ERROR_PIPE_BUSY`.
- `--jitter-max-ms` — случайная задержка между повторными попытками при "занято", которая нужна,
  чтобы разбить эффект "стада": несколько ожидающих, разбуженных одним и тем же освободившимся
  инстансом пайпа, иначе все одновременно повторят попытку, и выиграть сможет только один.

## Запуск

`sockrelay-client` демонизирует сам себя: форкается, отсоединяется от управляющего терминала
(`setsid`), и возвращает управление вызвавшему только после того, как старт получил понятный
результат — поэтому его безопасно вызывать синхронно из shell-профиля, без завершающего `&`, не
подвешивая старт шелла. `--foreground` пропускает всё это — без форка, без отсоединения — когда
супервизор процессов (systemd, container entrypoint) и так ожидает владеть этим процессом напрямую,
либо для интерактивной отладки; return code в этом случае — просто код этого же процесса, поскольку
отдельного демона, который бы отчитался о результате, нет.

"Понятный результат" — это больше, чем просто "bind и spawn прошли успешно": `sockrelay-server`
при старте проверяет, существует ли вообще named pipe по указанному `--pipe-path` (быстрая,
неблокирующая проверка — она не ждёт занятого агента, а просто подтверждает, что *хоть кто-то*
слушает под этим именем), и сразу завершается, если нет. `sockrelay-client` даёт спаунутому
серверу небольшой grace period (500мс), чтобы доказать, что он всё ещё жив, прежде чем объявить
успех — специально чтобы поймать именно эту ошибку (неверный `--pipe-path` или отсутствие
реального агента), а не обнаружить её только на первом реальном соединении, возможно намного
позже.

Return code отражает реальный результат:

- **`0`** — либо стартовал заново (печатает `sockrelay-client: started` в stderr), либо инстанс
  на этот сокет уже был запущен (не печатает ничего — это обычный случай при каждом следующем
  входе в шелл, не стоит объявлять о нём каждый раз). Оба случая означают для вызывающего "агент
  поднят".
- **не 0** — реальная ошибка старта (не смог забиндить сокет по настоящей причине, не смог
  заспаунить Windows-сервер, сервер сразу завершился — например, указанный пайп не существует).
  Диагностику печатает сам бинарник в stderr, поскольку вывод перенаправляется только *после*
  успешного старта — никакой `|| echo ...` на уровне шелла не нужен, чтобы увидеть сбой.

```sh
sockrelay-client
echo "запустился: $?"
```

Вызову из shell-профиля достаточно экспортировать `SSH_AUTH_SOCK` только после подтверждённого
старта — хватает `&&`, поскольку при сбое уже печатается своя диагностика и ненулевой код:

```sh
sockrelay-client && export SSH_AUTH_SOCK=~/.ssh/agent.sock
```

## Логирование

`--log-file`, не задан по умолчанию, определяет, куда *также* попадают таймстампированные
диагностические сообщения после демонизации — как собственные сообщения `sockrelay-client`, так и
сообщения спаунутого `sockrelay-server` (его stderr запайплен и пробрасывается дословно в тот же
sink, поскольку он вообще не знает о существовании лог-файла или `--log-file` этого процесса —
просто пишет в свой stderr ровно так же, как при прямом запуске). Если `--log-file` не передан,
файл вообще никогда не открывается — никакого неявного fallback-пути вместо "файла нет" тут нет.

Попадает ли диагностика *также* в stderr — вопрос полностью независимый от `--log-file`,
определяется демонизацией, а не флагом: до успешного старта — всегда да (это и позволяет ошибке
старта сразу всплыть у того, кто вызвал команду — см. [Запуск](#запуск) выше) — а после успешного
*демонизированного* старта — перестаёт, поскольку `detach_stdio` в этот момент и так освобождает
терминал. С `--foreground` отсоединения вообще не происходит, так что вывод продолжает идти и в
stderr, и в `--log-file` (если задан) всё время жизни процесса — естественное поведение для того,
за чем супервизор или интерактивный пользователь наблюдают напрямую.

```sh
sockrelay-client --log-file ~/.cache/sockrelay/client.log
```

## Сборка

Windows-часть кросс-компилируется под `aarch64-pc-windows-msvc` через
[`cargo-xwin`](https://github.com/rust-cross/cargo-xwin) — собственный binfmt interop WSL
выполняет кросс-компилированный `.exe` **нативно** (без Wine/эмуляции, поскольку архитектура
процессора та же самая) — именно это позволяет всей системе работать целиком из shell WSL, ни разу
не обращаясь к отдельной Windows-сессии.

```sh
rustup target add aarch64-pc-windows-msvc
cargo install cargo-xwin

cargo build -p sockrelay-client
cargo xwin build -p sockrelay-server --target aarch64-pc-windows-msvc
```

`install.sh` автоматизирует это (определяя реальную архитектуру хоста, а не предполагая
`aarch64`) и ставит оба release-бинарника в `/usr/local/bin`. Он не трогает никакие
shell-конфиги и не останавливает никакой уже запущенный мост агента — только печатает, что и
куда добавить, оставляя саму настройку тебе:

```sh
./install.sh
```

## Тестирование

```sh
cargo test --workspace
cargo clippy --workspace --all-targets
```

`server/src/pipe.rs` помечен `#![cfg(windows)]`, поэтому сборка для host выше компилирует для него
только пустой модуль — его реальная логика и тесты собираются только под Windows-таргет:

```sh
eval "$(cargo xwin env --target aarch64-pc-windows-msvc)"
unset CARGO_TARGET_AARCH64_PC_WINDOWS_MSVC_RUNNER
cargo test -p sockrelay-server --target aarch64-pc-windows-msvc
cargo clippy -p sockrelay-server --all-targets --target aarch64-pc-windows-msvc
```

(`cargo xwin test`/`cargo xwin run` выставляют
`CARGO_TARGET_AARCH64_PC_WINDOWS_MSVC_RUNNER=wine`, который здесь не установлен и не нужен — WSL
interop и так запускает бинарник напрямую, — поэтому переменная явно снимается перед обычным
`cargo test`/`cargo build`.)

`cargo clippy --workspace --all-targets --target aarch64-pc-windows-msvc` **не имеет смысла**:
`sockrelay-client` — целиком unix-специфичный код без Windows-совместимых заглушек, поэтому
кросс-компиляция всего workspace под Windows падает на не относящихся к делу ошибках в этом
крейте. Валидная сборка под Windows-таргет — только `-p sockrelay-server`.

## Заметки по безопасности

- Unix-сокет создаётся с временно ограниченным umask процесса, чтобы права доступа получались
  ровно такими, как в `--socket-mode` — без окна между bind и `chmod`, где сокет ненадолго
  существует с более широкими правами.
- Файловый лок, действующий только на старте, защищает от гонки двух инстансов, пытающихся
  одновременно переиспользовать один и тот же "зависший" путь сокета, оставшийся после
  нечистого завершения предыдущего процесса.
- Relay никогда не повторяет попытки и не респаунит после начального холодного старта: если
  соединение со спаунутым Windows-процессом умирает, демон завершается, а не маскирует сбой.
  Перезапуск ожидается от супервизора (systemd, менеджер процессов), как для любого другого
  упавшего демона.
- Занятый/насыщенный агент даёт честный, ограниченный по времени отказ (`--connect-timeout-secs`),
  а не бесконечное зависание или молча повторенный запрос.
